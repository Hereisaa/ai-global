# 10 — 模型調度守則（委派、選模、驗證）

> 對應病灶：指揮官下場（主對話自己做大量讀取，context 被擠爆）與自驗偏誤（做的人自己驗自己）。
> 派工 prompt 直接套 [30-templates.md](30-templates.md) 的模板。

## 第一原則：指揮官不下場

主對話的 context 是全 session 最貴的資源——它裝著使用者的原始要求和任務主線，被原始檔案內容擠掉就再也回不來。所以：**大量讀取、掃 repo、查網頁、批次改檔，一律派 subagent；主對話只進結論。**

### 觸發表（符合任一列就派，不要心存僥倖）

| 情境 | 動作 |
|---|---|
| 預估要讀 >3 個檔案、或 >400 行 | 派搜尋/探索 agent，只收結論與 `檔案:行號` |
| 要掃目錄樹、找「某東西在哪」、盤點命名慣例 | 派探索 agent（Claude Code 用 `Explore` 型） |
| 要查網頁、外部 API 文件、函式庫用法 | 派研究 agent，回報摘要＋來源 URL |
| 同型修改 ≥3 個檔案（改名、換 API、加欄位） | 派實作 agent；互不相依就平行派多個 |
| 審查、驗收、第二意見 | 一律派 fresh-context agent（見下方「驗證不自驗」） |

### 例外（自己做，不派）
- 已知精確位置的單點讀寫（如「改 `lib/watchlist.ts` 第 40 行那個函式」）。
- 涉及 ≤2 個檔案、總量 <50 行、且不需要先搜尋定位的小修。（檔數與行數**任一**超標就派，不要自我通融。）
- 與使用者的來回對話、決策、綜合判斷——這是指揮官唯一不可外包的工作。

> **Plan 關卡仍然有效**：派「會改檔」的 agent（實作／重構／批次修改）之前，仍受全域規則約束——除非使用者已要求自動執行、或正在執行已核准的計畫，否則先向使用者提出 Plan 取得同意，再派工。唯讀類（搜尋／研究／驗收）不需 Plan 關卡。

## 派工三件套（缺一就不准送出）

每個派工 prompt 必含：
1. **目標與動機**：要做什麼、為什麼做（agent 沒有你的對話脈絡，動機能讓它在邊角情境做對取捨）。
2. **驗收條件**：完成的可驗證定義，逐條列出（能跑的指令、該存在的檔案、該回答的問題）。
3. **回報格式**：明確規定回什麼、多長、長產物落到哪個路徑。

## 顯式指定 model（與 effort）

### 任務 → 模型對照表

| 任務性質 | 模型檔次 | Claude Code 對應 |
|---|---|---|
| 機械性：改名、格式化、套模板、單純關鍵字搜尋 | 最便宜 | `haiku` |
| 標準實作、程式搜尋、整理歸納、一般研究（**預設**） | 中階 | `sonnet` |
| 架構設計、卡關除錯、審查仲裁、安全敏感、多方案評審 | 最高階可用 | `opus` |

- 不確定選哪檔 → 先用中階跑，驗收不過再升級（見升降級路徑）。
- 派工時**顯式寫出 model 參數**，不要吃 harness 預設——預設可能是比你想的更貴或更弱的檔次。

### effort（誠實標註各環境差異）
- Claude Code 的 `Agent` 工具**沒有 effort 參數**（只有 model）——無法逐工調 effort 是正常的，不要去找不存在的參數。只有當環境提供 `Workflow` 工具時（大規模多 agent 編排，且需使用者明確同意才可用），其 `agent()` 才支援 `effort`（low/medium/high/xhigh/max）：機械段 `low`，驗證/仲裁段 `high` 以上。
- Codex 以 `~/.codex/config.toml` 的 `model_reasoning_effort` 控制整個 session，無法逐工調整。
- 規則：**能逐工指定就逐工指定；不能就在任務開始前確認 session 級設定符合任務檔次。**

## 回報合約（寫進每個派工 prompt）

subagent 回報只准包含：
- 結論（answer-first，一段話）
- 關鍵證據：`檔案路徑:行號`，或指令與其輸出的關鍵行
- 風險與未解事項（沒有就寫「無」）

限制：
- 全文 500 字內。超過 50 行的產物（報告、diff、清單）**落檔**（scratchpad 或指定路徑），回報只給路徑＋三行摘要。
- 禁止貼整個檔案內容、禁止流水帳式過程描述。

## 升降級路徑

- **升級**：同一任務驗收失敗 2 次 → 禁止第三次原樣重試。三選一：(a) 升一檔模型重派；(b) 把任務拆小再派；(c) 換方法（先讀 [20-judgment.md](20-judgment.md)「方向錯誤訊號」判斷是執行問題還是方向問題——方向錯了升級模型也沒用）。
- **降級**：高檔模型已完成一件樣板後的同型重複工作 → 降檔批量跑，完成後抽驗其中一件（用驗收 agent），抽驗不過才全檢。

## 驗證不自驗（鐵律）

**執行者不得當自己的驗收者。**同一個 context 寫的東西，同一個 context 驗，會把意圖當成事實。

- 驗收一律派 **fresh-context agent**：只給它「驗收條件＋產出位置」，**不給**執行過程與執行者的自述，避免被帶風向。
- **檔案產出** → read-back：驗收者實際打開檔案，逐條核對驗收條件與內容完整性（不是看檔案存在就過）。
- **程式碼** → 實跑：專案的 test / typecheck / lint 指令（查專案 CLAUDE.md 的指令速查），必要時實際啟動功能操作一遍。「編譯過」不等於「行為對」。
- **高風險判斷**（架構選型、資料遷移、安全、對外發布內容）→ 第二意見：另派一個 agent 不看第一份答案獨立作答，比對分歧；或產 2–3 個方案後派評審 agent 選優並說明理由。
- 驗收者回報格式：逐條 `PASS/FAIL + 證據`；任何一條 FAIL，任務就回到執行者，不得「大致通過」。

## 各 harness 能力備忘（2026-07 現況，過時就更新本節）

- **Claude Code**：`Agent` 工具派 subagent（型別：`Explore` 唯讀搜尋 / `Plan` 規劃 / `general-purpose` 通用 / `claude` 萬用），互不相依的多個派工放在**同一則訊息**裡平行執行；背景執行是預設。大規模多 agent 編排若環境提供 `Workflow` 工具才可用，且需使用者明確同意；沒有就用多個 `Agent` 呼叫。
- **Codex（桌面版）**：無同款 subagent 工具。fallback：任務自行分段、驗證改用「開新對話貼驗收條件」或請使用者另開 session 驗收。本節若與實際工具不符，以實際環境為準並回寫本檔（流程見 [40-maintenance.md](40-maintenance.md)）。
