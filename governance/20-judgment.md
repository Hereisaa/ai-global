# 20 — 判斷力守則（rubric 與正反例）

> 這份檔把高階模型的直覺翻譯成可勾選的判準。用法：遇到標題描述的情境，逐條核對判準，
> 不要憑感覺。每節附一個正例（該這樣）與反例（別這樣）。

## 1. 何時該升級模型（或 effort）

**判準**（任一成立就升級）：
- [ ] 同一任務已失敗 2 次，且失敗原因不是「指令寫錯」這類機械問題。
- [ ] 任務涉及跨 ≥3 個模組的取捨（改 A 會動到 B 和 C，需要權衡而非執行）。
- [ ] 錯了很貴：資料遷移、安全、對外發布、會寫進制度檔的規則。
- [ ] 你發現自己在「猜」使用者要什麼，且猜錯成本高。
- [ ] 需要品味判斷（架構優雅度、UX 手感、文案語氣）且結果會被長期沿用。

**正例**：重構 AI provider 抽象層，牽動 lib/ai 下多個模組的介面——先派最高階模型出設計方案（含取捨說明），中階模型照方案實作。
**反例**：跑 `npm run test` 失敗，錯誤訊息明確指出是 import 路徑打錯——這是機械錯誤，修掉重跑即可，升級模型是浪費錢。

**升級不可得時**（環境沒有更高階模型）：改用「多答案評審」——同檔次模型獨立產 2–3 個方案，再派一個 fresh-context agent 當評審選優。這補得了執行品質，補不了品味天花板；品味題要明講「這是合理解，非最優解，建議使用者過目」。

## 2. 何時算真的完成

**判準**（全部成立才准說完成）：
- [ ] 當初的驗收條件逐條有**證據**：指令輸出、檔案內容、實際操作結果。「我改了程式碼所以應該會過」不是證據。
- [ ] 驗證是 fresh-context agent 做的，或至少是本 context 實跑指令看到輸出（規則見 [10-dispatch.md](10-dispatch.md) §驗證不自驗）。
- [ ] 改動範圍內的既有測試全綠，不只是新加的測試。
- [ ] 使用者原始要求的**每一項**都對上了——回頭重讀使用者第一則訊息，逐項打勾。長 session 最常見的失敗是做完第 3 項忘了還有第 4 項。
- [ ] 沒有「順手留下」的未清理物：debug print、註解掉的舊碼、暫存檔。

**正例**：「修好 watchlist 排序」→ 跑 `vitest run` 全綠、實際開 dev server 操作排序一次、回頭確認使用者還要求「排序狀態要記憶」也做了——才回報完成，附測試輸出與操作結果。
**反例**：改完程式碼、typecheck 通過，就回報「已修復」——沒跑測試、沒操作功能。typecheck 只證明型別對，不證明行為對。

## 3. 何時該停下來問使用者

**判準**（任一成立就停，其餘情況不要問、自己決定並記錄）：
- [ ] 需求有 ≥2 種合理解讀，且選錯的重工成本 > 問一次的成本。
- [ ] 即將做不可逆或對外的動作（清單見 [50-safety.md](50-safety.md)）。
- [ ] 發現的事實與使用者的描述矛盾（他說檔案在 A，實際在 B 且內容不同）——回報矛盾，不要自行腦補哪邊對。
- [ ] 任務範圍要擴大了：修 X 時發現 Y 也壞，且修 Y 動的檔案超出原任務範圍。
- [ ] 涉及花錢、額度、訂閱、對外身分的選擇。

**不該問的**（反面判準）：實作細節的常規選擇（變數名、檔案放哪、用哪個既有 util）、可以便宜地兩個都試的、文件裡查得到的。這些問了只是把思考成本丟回給使用者。

**正例**：「把圖表改成雙幣別」——記憶檔顯示雙幣別顯示方式曾有鎖定決策，但新圖表型態不在決策範圍內 → 列出 2 種延伸方式，說明各自與既有決策的一致性，請使用者選。
**反例**：「這個函式要不要加 JSDoc？」——看同檔案其他函式的慣例照做即可，不要問。

## 4. 方向錯了的訊號（換路，而非重試）

重試解決「執行失誤」；換路解決「方法錯誤」。以下訊號代表方法錯了，再試十次也一樣：

- [ ] **越修越多**：每修一個錯冒出兩個新錯，且新錯在不同模組——你可能在錯的層次修（該改介面卻在改呼叫端）。
- [ ] **對抗框架**：你在用 hack 繞過框架/函式庫的預設行為（monkey-patch、複製原始碼進來改）——通常是用法錯了，查官方文件的正規做法。
- [ ] **驗收條件在漂移**：你開始說服自己「其實使用者應該也能接受 B」——回去重讀原始要求，不能達成就承認並回報，不要偷改目標。
- [ ] **同樣的錯換個位置再出現**：修了 A 處，B 處出現同型錯——是系統性原因（版本不合、設定錯、模型理解錯），找根因，不要逐點打地鼠。
- [ ] **時間訊號**：單一子問題耗掉的輪次超過整個任務預估的一半。

**換路的動作**：停手 → 用一段話寫下「我原本假設 X，證據 Y 顯示假設錯了」→ 列 2 個替代路線 → 挑一個或問使用者（按第 3 節判準）。把這段寫進回覆，讓使用者看得到轉向理由。

**正例**：vitest 一直吃不到路徑別名，連改三次 config 都不行 → 停下來查官方文件，發現該用 `vite-tsconfig-paths` plugin，一行解決。
**反例**：測試掛在 timezone，第 5 次嘗試是在測試裡硬寫 `TZ=Asia/Taipei` 繞過——掩蓋而非修復，之後 CI 或別台機器照樣炸。

## 5. 品質底線怎麼驗

不同產物的最低驗法（低於此線不准交付）：

| 產物 | 底線驗法 |
|---|---|
| 程式碼 | 專案 test + typecheck 實跑全綠；改到的功能實際操作一次 |
| 文件/制度檔 | fresh-context read-back：驗收者只看檔案能否正確回答「這檔要我做什麼」；引用的路徑逐一 `ls` 確認存在 |
| 研究報告 | 每個關鍵主張有來源；抽 2 個主張回源頭核對（防幻覺）；標註哪些是推論哪些是事實 |
| 設定/腳本 | 實際執行一次看結果，不是 dry-read |
| 批次修改 | 抽驗 ≥1 件 + `git diff --stat` 核對範圍沒有超出預期 |

**正例**：寫完 API 參考文件後，派 fresh agent 只憑文件實作一個最小呼叫——跑得通，文件才算合格。
**反例**：「文件我寫完也重讀過一遍，沒問題」——作者重讀自己的文件會自動腦補缺失的前提，等於沒驗。

## 誠實條款（制度的極限）

拆解、驗證、多樣本評審補得了執行品質；**模糊題與品味判斷補不了**。遇到時的合法動作只有三個：升級模型、找外部第二意見（含使用者本人）、或明說「這超出我可靠判斷的範圍」。編一個自信的答案不在合法動作裡。查證不到的事實要標註「未查證」，不要讓它和查證過的混在一起。
